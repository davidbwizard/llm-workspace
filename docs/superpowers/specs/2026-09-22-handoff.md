## What is next -- David's direction, 2026-09-22

**A lightweight tagging system, and grouping in the sidebar.** His words:
"basically it will be a config to group by sessions is a directory and create a
light weight tagging system. I mean light weight."

Two entry points, both of which already exist as surfaces:

1. **The card menu** gains an item to pick an existing category, or create one
   and put this session in it.
2. **The launch dropdown** -- the split button shipped in `dd304d5` -- gains
   the same, so a session can be categorised as it starts. This is why that
   dropdown was built as a container for options rather than a name field.

### The decision to make first, or this gets built twice

**What does a category attach to?** This is the same question that governs
Nate's rename, reorder and hide requests, and it has to be answered once for
all of them. A pid dies with the process. A session id is gone tomorrow. If a
category is attached to either, it evaporates and the feature is useless the
next morning.

**Attach it to the FOLDER.** It survives, it needs no reconciliation, and it
makes David's own "group by directory" fall out for free: sessions in a folder
inherit that folder's category, so grouping by category and grouping by
directory become the same mechanism rather than two. `favourites.ts` is the
precedent and probably the store to extend -- already per-folder, already
persisted, already shared between the launch bar and the conversation header.

The awkward case to decide deliberately rather than discover: **several
sessions in one folder**. They share a category, so the sidebar shows the group
once with several sessions under it -- which is probably what "group" should
mean anyway.

### What "lightweight" should mean

- **One category per folder**, not many tags. "Select a category" is singular,
  and one is the version that stays simple.
- **A name and nothing else** to begin with. No colours, no icons, no
  hierarchy. Add a colour only if the sidebar proves hard to scan without one.
- **No category is the normal state.** Uncategorised sessions are not an error
  and must not be herded into an "Other" group that grows forever.

### Ordering, and the thing it fixes

Nate asked to reorder the sidebar; David independently said "having the cards
shift is annoying actually". They are one job. There is a cheap first step
worth taking before any of the above: **the rail re-sorts by activity, so cards
move while you are looking at them.** Ordering by session start instead makes
the order stable with no store, no persistence and no identity decision. Manual
reorder can come later on top of a stable base.

Also: **Cmd+1-9 is defined by sidebar order**, so grouping, reordering and
hiding all silently redefine what Cmd+3 opens. Probably desirable; make it a
decision.

## Two working rules learned the hard way today

1. **Cap test workers.** Three agents each running `npm test` put 88 node
   processes and 5.8 GB on David's machine while he was using it. The command
   is `npx vitest run --maxWorkers=2 --minWorkers=1` -- **both bounds**, or it
   errors and prints `Test Files no tests`, which reads like a pass.
   `--poolOptions.threads.*` silently caps nothing here, because this repo sets
   no pool and vitest 2.x defaults to forks.
2. **Worktrees work now.** `ln -s <main>/node_modules node_modules` in a
   worktree root makes the full suite and the typecheck run there, and the
   symlink is already gitignored. That removes the reason agents were put in
   the shared checkout, where they collided twice today -- both times because
   this session checked out a branch under a working agent.
